lektyra · how voices are matched

From two seconds of speech to “that is the same voice”

No transcription model and no LLM decides who is speaking. A small local network turns the voice into numbers, and plain arithmetic in lektyra's own code compares them. Here is every step, with the real numbers from the five test videos.

1A voice becomes 192 numbers

Every 2 seconds of speech (a new window every second) go through SpeechBrain ECAPA, an open-source speaker-recognition network trained on thousands of voices. It does not understand words. It measures how a voice sounds (pitch range, timbre, resonance) and writes that down as 192 numbers: a voice fingerprint. The same person gives similar numbers in any language and any sentence.

A GPU is not needed. Even a small 4-core server would stay far ahead of a live stream (estimate); a GPU only matters for many streams at once.

2Similarity is an angle

Think of each fingerprint as an arrow from the origin. lektyra makes every arrow the same length, so only its direction carries the voice. Two arrows of the same voice point almost the same way; a different voice points elsewhere. The measure is the cosine of the angle between them: 1 means the same direction, 0 means unrelated. Computing it is one multiplication per number and a sum: 192 multiplications.

Drawn in 2 dimensions; the real arrows have 192, but the angle works the same way.

3One video: grouping the windows into speakers

A 57-minute debate gives about 3,200 fingerprints. lektyra groups them: the two closest groups merge, again and again, until the closest two are further apart than a set distance (0.55). What is left are the speakers of that video, S1, S2, S3, numbered by how much they talk. Groups with under 1 % of the speech become “unclear” instead of a speaker. Each speaker's average arrow is its centroid.

A sketch of the idea, not real fingerprints. On video A this gave S1 50 %, S2 37 %, S3 11 %, plus two brief voices.

A.S2 and B.S1 are the second voice of both duels (0.92). A.S3 and C.S2 are the same moderator (0.87). Every pair of different voices stays at 0.47 or below. The gap between 0.47 and 0.80 is what makes a safe threshold possible.

5Profiles: matching a new voice (try it)

A profile is simply the stored, confirmed fingerprints of a named person, often from different rooms. A new voice is compared with all of them, the 5 nearest are taken, they vote, and the result is checked against two thresholds. Drag the dot round the circle (or use the slider). Then confirm it as a person: the profile gains a sample, and the next nearby voice matches.

    Thresholds from the voices report: ≥ 0.70 named automatically (still shown to a human), 0.55–0.70 suggested, below 0.55 unknown. A wrong name is worse than “unknown”.

    Person 1 has two clusters: studio and parliament hall. That is why lektyra keeps all samples instead of one average per person: a new hall recording finds the hall samples. When a human names an “unknown”, its fingerprints become new samples and the profile is rebuilt from them. Nothing else changes.

    6pgvector: the database that finds the nearest voices

    pgvector is an extension for PostgreSQL (lektyra's local database has version 0.8.6). It adds a column type that holds a fingerprint, and operators that measure the distance between two of them. Finding the nearest samples is then an ordinary query: sort by distance, take the first k.

    -- one row per confirmed 2 s sample of a person
CREATE TABLE voice_sample (person_id bigint, embedding vector, embedding_model text, …);

-- the 5 stored samples nearest to a new fingerprint $1
SELECT person_id, 1 - (embedding <=> $1) AS similarity
FROM   voice_sample
WHERE  embedding_model = 'ecapa-voxceleb'
ORDER BY embedding <=> $1      -- <=> is cosine distance = 1 - similarity
LIMIT  5;

    Without an index the database simply measures the distance to every row. For lektyra's scale (thousands of samples) that takes milliseconds. With millions of rows, an HNSW index makes it fast: the samples are linked into a graph with a few layers, like a road map with motorways, main roads and streets. The search starts at the top, always jumps to the neighbour closest to the target, drops a layer when no neighbour is closer, and ends among the nearest samples at the bottom. It checks a few dozen points instead of all of them. It is approximate, so it can occasionally miss the very nearest one, which a vote over 5 neighbours tolerates.

    -- only when the table grows large
CREATE INDEX ON voice_sample USING hnsw ((embedding::vector(192)) vector_cosine_ops)
  WHERE embedding_model = 'ecapa-voxceleb';
